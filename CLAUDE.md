## What this is

A subscription-tracking web app (Next.js + Supabase + Vercel) being built from a PRD: manual and Gmail-detected subscription tracking, a spend dashboard, renewal/trial reminders, and a cancellation-link directory. The active build plan (schema, Gmail detection design, design system, milestone order) lives in the session that created this repo — there is no in-repo plan doc yet, so infer intent from the PRD-shaped structure below (migrations, `detected_candidates`, `reminder_log`, etc.) rather than assuming a generic CRUD app.

## Next.js 16: do not rely on training data here

This repo runs Next.js 16, which has real breaking changes vs. most training data. Before writing routing, auth, or data-fetching code, check `node_modules/next/dist/docs/` (bundled, version-matched docs) rather than assuming Next 13/14/15 conventions. Two that already bit this codebase:

- **`middleware.ts` is renamed to `proxy.ts`** (`export function proxy(...)`, not `export function middleware(...)`). The root `proxy.ts` here does session-cookie refresh and redirects unauthenticated requests to `/login`.
- **Server Actions ("Server Functions") are not guaranteed to be covered by the proxy matcher** — Next's own docs warn a Server Action is invoked as a POST to whatever route defines it, so a matcher change or a refactor that moves the action can silently drop proxy coverage. Every Server Action must independently re-check auth (see `requireUser()` in `lib/supabase/server.ts`) rather than trusting `proxy.ts` alone.
- `cookies()`, `headers()`, route `params`/`searchParams` are async-only (no sync fallback).

`AGENTS.md` (imported above) is regenerated by `next dev`/`next build` itself — don't fight it; commit it if it reappears in a diff.

## Architecture

**Auth & data access layers** (`lib/supabase/`) — three separate Supabase client constructors, each with a distinct trust boundary:
- `client.ts` — browser client, anon key, used from Client Components (e.g. `components/auth/AuthForm.tsx`).
- `server.ts` — RLS-scoped server client for Server Components/Actions/Route Handlers, bound to the request's cookies. Exports `requireUser()`, which every mutating Server Action should call first (see the proxy caveat above).
- `admin.ts` — service-role client (`import "server-only"` guarded). Bypasses RLS entirely. Reserved for cron routes, the Gmail OAuth/scan pipeline, and admin-only writes (e.g. the `providers` directory). Never import this outside those contexts.
- `proxy.ts` (in `lib/supabase/`, distinct from the root `proxy.ts`) — the session-refresh + redirect logic the root proxy delegates to.

**Route groups**: `app/(auth)/` (login/signup, unauthenticated), `app/(app)/` (dashboard/subscriptions/candidates/settings — server-side auth-gated in `app/(app)/layout.tsx`, redirects to `/login` if no user), `app/auth/callback/` (OAuth code exchange, outside both groups since it's a fixed redirect target). The root `proxy.ts` matcher is the first line of auth defense; the `(app)` layout's own `getUser()` check is the second, since proxy coverage isn't guaranteed for every code path.

**Database** (`supabase/migrations/`, numbered and applied in order): tables model the PRD's subscription object directly —
- `subscriptions` is the core record (identity, billing, status, purchase info, management URLs, detection metadata). Its `user_verified_fields text[]` / `is_user_verified` columns exist specifically so automated (email) re-detection never silently overwrites a field the user manually edited — any code that merges a detected candidate into an existing subscription must check this array first.
- `providers` is the admin-maintained cancellation-link directory (public read, service-role-only write — no insert/update/delete RLS policy is intentional, not an oversight).
- `gmail_connections` stores encrypted OAuth tokens and has **no RLS policy granted to `authenticated`/`anon` at all** (default-deny by omission) — only the service-role client touches it.
- `detected_candidates` is the pre-confirmation staging table for Gmail-detected subscriptions; confirming/rejecting a row is what promotes it into (or merges it onto) a `subscriptions` row.
- `reminder_log` has a `unique(subscription_id, reminder_type, cycle_key)` constraint that is the idempotency mechanism for the (not-yet-built) reminder cron — insert-then-check, don't send a reminder without it.
- Every user-owned table has an `auth.uid() = user_id` RLS policy; `categories` additionally allows reading rows where `user_id is null` (system defaults, seeded in `0009_seed_categories.sql`).

Migrations are applied to the live Supabase project via the Supabase MCP tools (`apply_migration`, `list_tables`, `get_advisors`), not the Supabase CLI — there is no local Postgres/Supabase CLI setup in this environment. After any DDL change, re-run `get_advisors` (security) to catch missing RLS or mutable-search-path issues before moving on.

**Design system** (`app/globals.css`, Tailwind v4 CSS-first config — no `tailwind.config.ts`): dark-first theme, tokens defined as CSS variables under `:root` and mapped via `@theme inline`. One accent color (`--accent`, signal-lime) used sparingly against near-black surfaces (`--background`, `--surface`, `--surface-raised`). `components/ui/` are hand-rolled primitives (Button, Card, Badge, Input) styled directly against these tokens with `class-variance-authority` + `cn()` (`lib/utils.ts`) — not shadcn/ui-generated (the shadcn CLI's registry host is unreachable from this environment's network egress policy, along with several other external design-reference sites). Extend this token set rather than hardcoding colors in components.

**Environment variables**: `.env.local.example` documents everything needed (Supabase URL/keys, a *separate* Google OAuth client for Gmail scanning distinct from whatever provider Supabase Auth's Google sign-in uses, token encryption key, Resend, cron secret, optional Anthropic key for LLM-assisted entity extraction). `.env.local` itself is gitignored except the `.example` file, which is explicitly un-ignored in `.gitignore`.
